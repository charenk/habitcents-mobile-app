## 2026-09-06 additions (navigation wave: filled tab glyphs, segment pagers, branch hygiene)

- **The tab bar's selected state is now a filled glyph, not a pill (supersedes the pill half of ADR 0037, shipped in PR #143).** `components/ui/TabBarIcon.tsx` draws no surface at all: active = filled glyph, inactive = outlined, plus the heavier label that was already there. Generalised again by `utils/upcomingGroups.ts`: month groups with per-month row scoping, so rows sum to their header, headers sum to the card, and the card is still `upcomingWindowTotal` untouched. **When two numbers on one screen disagree, look for two definitions before looking for a bad multiply.**
- **`datePrecision` is the session's one genuinely new idea.** Charen: "sometimes I may not know when exactly it will happen... I ended up clicking 15 days for example. Later realized, when I see the saved list, the sample I entered as 15 days now really reads like the expense is about to happen in 15 days." The app forced a date, so it made the user invent a number and then rendered the invention back as a confident prediction. Charen's own framing made it tractable: **the cadence does the bucketing, and only the day is unknown.** So `Expense.datePrecision` is `'day'` or `'month'`, optional, absent meaning `'day'`; under `'month'` the stored date is the LAST day of the named month with rule `{ type: 'monthly', monthDay: 'last' }` (legacy monthly steps the same day-of-month, so a Jan 31 anchor rolls to Mar 3 and would file a February payment under March). **A named field, not a sentinel.** A sentinel date puts the meaning in a value every date comparison in the app silently participates in; a named field means a consumer that has not been taught about precision fails at REVIEW rather than at runtime. ADR 0042, amending 0024 and 0041.
- **The four guards precision had to buy, and why each one is not optional.** `admits` accepts a month-precision occurrence when the window reaches its MONTH ("is a December bill before December 10" is a question the stored data cannot answer, and the app must not invent one). `advancePastToday` must not advance a non-`'day'` item: its premise is that the materializer already wrote today's occurrence into Spent, and for an unknown-day bill the materializer deliberately wrote nothing, so without the guard the bill vanishes from its own month on the 30th. `occurrencesToMaterialize` returns `[]`. `scheduleParts` forces the qualifier to `null`, which is **the only thing standing between the storage anchor and a spoken claim**: without it VoiceOver says "Last day" for a day the user explicitly said they did not know. `groupUpcomingByMonth` needed no change at all, which was the design's best property.
- **A consequence you write down and accept is still a consequence.** ADR 0042's first draft accepted that "an unknown-day recurring bill never graduates into Spent": honest, since the app does not know it happened, but it meant a user who sets Rent this way has a Spent tab that never shows their rent. Reading it back the same day, the right answer was obvious: the app cannot know, so it ASKS. The current month's row carries a check that writes a child dated today in the materializer's own shape, and `dropPaidMonths` enforces ADR 0024's one-occurrence-one-tab invariant at MONTH resolution, mirroring the materializer's own `(parentId, date)` idempotency. ADR amended the same day. **Writing a consequence down is what makes it reviewable; accepting it is a separate decision, and "permanent" in a draft is a prompt, not a verdict.**
- **A layout choice made from a description is a guess until it is on a screen.** Charen picked the cadence badge's left-column placement from my written description, and corrected it on device: three lines on the left put the widest element on the row's bottom edge. Under the amount, the columns balance and rows lose about 20pt each, which matters at ~40 rows. Related and separate: the badge's text **rode high inside its pill** because `justifyContent: 'center'` centres the text's BOX, and Inter's box carries a descender that "Monthly" only partly fills, so the visible ink sat off centre. Fixed by sizing the pill from padding around a tightened `lineHeight`, which also keeps the house "minHeight, never height" rule intact because padding still grows with Dynamic Type.
- **`numberOfLines={1}` on text that has outgrown its line box CROPS it rather than shrinking it.** At XXXL the card's count line rendered as a band of half-glyphs. Chrome text caps at 1.5 (`utils/textScale.ts`, matching SegmentedControl and the tab bar) and wraps; the total itself stays uncapped because it is content, not chrome. Same session, same rule at row level: at AX1+ `ExpenseRow` and its three siblings STACK, because the name and the amount are both content and capping either would invert the house rule. `EmojiTile`'s glyph is the app's only `allowFontScaling={false}`: an 18pt emoji rendered near 42pt inside a 36pt tile and clipped to a sliver, and it is defensible precisely because nobody READS it.
- **Chips size to their label, so a grid of them is ragged.** 31 unconstrained day cells wrapped into rows of 8/7/6/6/4. `Chip` gained a `width` prop for fixed grid cells. `MonthDayPicker` is built entirely from `Chip` on purpose: there is no date picker anywhere in this repo and adding `@react-native-community/datetimepicker` would touch `package.json`, which `scripts/ota-eligible.sh` treats as a native path, forcing a build instead of an OTA.
- **Accessible names collide across rails on one sheet.** The Add bill sheet has three rails that can carry the same word: "Gym" is a name preset AND a glyph, "Utilities" is a preset AND a category. Two tests broke on exactly this. Every glyph cell now speaks "*name* icon" and `Chip` gained `labelSpoken` so `CategoryChipRow` speaks "Utilities category". **A visual-only decomposition needs a spoken counterpart**: Upcoming's rows DRAW `scheduleParts` (arrow, date, badge) and SPEAK `describeSchedule` (the full sentence), the same split `labelSpoken` / `badgeSpoken` established in ADR 0040.
- **Declining the literal ask twice, with the reasoning recorded.** (1) Calendar-anchored windows are non-monotonic: on the 28th a "1 month" window is NARROWER than "2 weeks", so the three presets stayed durations and months became groups instead (ADR 0041). (2) A third precision `'none'` for a bill with no date at all was deferred: storage drops any row whose date will not parse, so an undated bill must still store a date, and whatever it stores makes it visible to six surfaces that read the raw expense list and filter on date, starting with Spent, which renders anything dated on or before today as a spend that already happened. A far-future sentinel makes all six correct by accident, which is what makes sentinels landmines.
- **THE PROCESS TRAP OF THE DAY: GitHub CLOSES a child PR when its base branch is deleted; it does not retarget it.** I merged an eight-deep stack bottom-up with `gh pr merge --merge --delete-branch` and a loop that waited for each child to retarget to main. It never did. Deleting #165's branch CLOSED #166, and my loop then merged #167 into the still-open intermediate branch `fix/dynamic-type-rows` instead of main, and deleting THAT branch closed #168. No content was lost (the stack was strictly linear and every branch was a superset of the one below), but two PRs were closed and one merged into the wrong base. **Recovery:** a PR whose base branch is deleted cannot be reopened, so push the deleted base ref back (`git push origin <sha>:refs/heads/<branch>`), reopen, retarget with `gh pr edit <n> --base main`, then merge. **The rule going forward: retarget each PR to main EXPLICITLY before merging it, merge without `--delete-branch`, and delete every branch at the end.** Also: retargeting changes the base, which re-triggers CI, so poll `mergeStateStatus` for `CLEAN` rather than trusting the previous green.
